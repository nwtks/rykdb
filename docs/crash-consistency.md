# クラッシュ整合性

RykDb が保証するクラッシュ整合性の契約と、その検証方法をまとめる。
実装は **.NET BCL の範囲**に限定する。ディレクトリ fsync・P/Invoke・
プラットフォーム固有のファイルシステム操作は使わない。

## 1. 保証レベル

| レベル | 障害                                                                                      | 保証                                                                                                                                         |
| ------ | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| C1     | プロセスの異常終了（kill -9・例外・fsync 失敗）                                           | **保証する**。COMMIT が成功して返った transaction の行は、再オープン後にすべて見える。未 COMMIT の行は見えない。                             |
| C2     | OS の再起動（ファイルデータの fsync は生き残るが、create / rename / delete が失われ得る） | **復旧を最善努力する**。保持している WAL と MANIFEST から復旧し、復旧できない場合は `CorruptionError` で停止する（黙ってデータを捨てない）。 |
| C3     | 電源断（ストレージのライトキャッシュも失われ得る）                                        | **保証しない**。C2 と同じ復旧を行うが、新規に作ったファイル名が失われると commit 済みデータを失い得る。                                      |

C2/C3 で `CURRENT` やファイル名の永続化を保証できないのは、
BCL がディレクトリの fsync を公開していないためである
（`File.OpenHandle` / `FileStream` はディレクトリを開けず `UnauthorizedAccessException` になる）。

## 2. 永続化の境界

| 操作                      | 使用する API                                          | 意味                                                         |
| ------------------------- | ----------------------------------------------------- | ------------------------------------------------------------ |
| 既存ファイルへの追記      | `FileStream.Flush(true)` / `RandomAccess.FlushToDisk` | ファイルデータを安定媒体へ書き出す                           |
| SSTable / MANIFEST の作成 | 書き込み後に `Flush(true)`                            | ファイル内容を安定媒体へ書き出す（名前の永続化は保証しない） |
| `CURRENT` の更新          | `CURRENT.A` / `CURRENT.B` の二世代                    | rename を使わず、世代番号と CRC で新しい方を選ぶ             |
| 不要ファイルの削除        | `File.Delete`                                         | すぐには行わず、復旧検証後の GC に回す（遅延削除）           |

## 3. 復旧の手順

1. `CURRENT.A` / `CURRENT.B` を試す。
   どちらも開けない場合だけ、MANIFEST ファイルを新しい順に試す。
   通常時に未反映の新しい MANIFEST を採用しない。
2. MANIFEST の編集履歴を先頭から適用し、**参照する SSTable がすべて存在する最後の Version** を選ぶ。
3. 現在の Version が壊れていれば、その Version を新しい MANIFEST にスナップショットして復旧する。
   古い MANIFEST は削除しない。
4. 残っている WAL をファイル番号順にすべて再生する。
   - COMMIT まで到達した Batch だけを適用する。
   - 各 WAL の不完全な末尾は、その WAL の最後の完全なフレームまで切り詰める。
   - 古い WAL の再適用は SeqNo の可視性で解決する。
5. `NextSeqNo` / `NextTxnId` / `NextFileNumber` を、MANIFEST・SSTable・WAL の最大値より後ろへ進める。
6. 復旧を完了してから、参照されていないファイルを起動時 GC の対象にする。

## 4. WAL の形式

WAL v2 は、ファイル先頭に 16バイトのヘッダー（magic・version・header CRC）を持ち、
各フレームは payload 長・payload CRC・ヘッダー CRC で構成する。

- ヘッダーが途中で切れている → 書きかけの WAL として扱い、フレームを読まない。
- ヘッダーの CRC 不一致 → `CorruptionError`。
- フレームヘッダーが途中で切れている → torn write として切り詰める。
- フレームヘッダーの CRC 不一致 → `CorruptionError`（長さ破損を torn write と誤認しない）。
- payload が途中で切れている → torn write として切り詰める。
- payload の CRC 不一致 → `CorruptionError`。

## 5. 遅延削除

次のファイルは、MANIFEST へ反映した直後には削除しない。

- WAL: rotate 後も残し、起動時の復旧が完了するまで削除しない。
- MANIFEST: rotation 後も残し、新しい `CURRENT` 世代の検証が完了するまで削除しない。
- compaction の入力 SSTable: 新しい Version の出力が検証できるまで削除しない。

削除は起動時の GC で行う。削除に失敗しても、次回の起動で再試行する。
削除が先に永続化されて新しいファイル名が失われるとデータ損失になるため、
削除は常に「新しい状態の検証後」に行う。

保持する世代は、WAL が最新 3本、MANIFEST が最新 4世代である。
これを超えた分だけを回収する。

## 6. 不変条件

復旧後に次を検査する。

- **CC-1**: COMMIT 成功済み transaction の全行が見える。
- **CC-2**: 未 COMMIT の行が見えない。
- **CC-3**: `Version.validate` を通る。
- **CC-4**: MANIFEST が参照する SSTable が存在し、Footer・索引・読んだブロックの CRC が正しい。
- **CC-5**: `NextFileNumber` がディスク上の全ファイル番号より大きい。
- **CC-6**: 復旧を 2 回繰り返しても同じ結果になる（冪等）。
- **CC-7**: 参照されないファイルは削除せず、`.orphans/` へ退避する。
- **CC-8**: 復旧不能時は `CorruptionError` / `IoError` を返し、ユーザーデータを書き換えない。
- **CC-9**: DDL はカタログと行が原子的で、半端な索引・スキーマを残さない。
- **CC-10**: 復旧処理中に再度クラッシュしても、次の open で同じ契約を満たす。

## 7. 検証

- 操作ログ: `Flush` / `File.Move` / `File.Delete` の順序をテスト用フックで記録し、期待順を検査する。
- 名前空間消失: 新規 WAL / SSTable / MANIFEST を消す、`CURRENT` を旧世代へ戻す、
  ファイルを先頭 N バイトへ切り詰める、などのイメージを復元して open する。
- プロセス kill: WAL 追記・fsync・MANIFEST 追記・rotate・compaction install・close の前後で
  子プロセスを kill し、再オープン後に CC-1〜CC-10 を検査する。
- 復旧中の再クラッシュ: 復旧処理の途中で再度 kill し、次の open で同じ契約を満たすか検査する。

## 8. 残る限界

- 新規 DB の作成直後、最初のファイル名が永続化される前の電源断。
- WAL rotate 直後の新 WAL 名、MANIFEST snapshot の新ファイル名、SSTable の新ファイル名の消失。
- 遅延削除で古い世代を削除した後の電源断。
- macOS の `F_FULLFSYNC` に相当する保証はない（`Flush(true)` は fsync のみ）。

これらは C2/C3 の範囲であり、C1 の保証には影響しない。
厳密な電源断耐久性が必要な場合は、ディレクトリ fsync を任意の
プラットフォーム別プラグインとして追加する（現行の実装範囲外）。
